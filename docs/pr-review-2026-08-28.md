### #24 Back up databases before migrations — MERGED

**Fixed (blocker): it killed the world.db self-repair.**
`DatabaseManager.Initialize()` already had a recovery path: if `world.db` is missing or has no
`ItemTemplates`, it is re-extracted from `datos/world.zip` and the server starts. The PR put
`DatabaseBackups.CreateBeforeMigration()` as the **first** statement of `Initialize()`, about 160
lines ahead of that block. `Create` opens both databases to verify the copy, so a corrupt,
truncated or half-extracted `world.db` throws, rethrows, and aborts `Initialize()`. A server that
used to heal itself now refuses to boot.

Applied: order is now **repair → back up → migrate**. The backup still precedes every migration —
which is the PR's actual goal — and now runs over a sound database.

**Fixed (blocker): the restore procedure corrupts the restore.**
`docs/database-backups.md` said to copy `auth.db` and `world.db` back into `bases/`. The databases
run in WAL mode, so a stopped server leaves `world.db-wal` and `-shm` behind — there is a 2 MB
`world.db-wal` in `bases/` right now with nothing running. Copy the backup in without removing them
and the next open replays the *previous* database's journal on top of it. The result is neither the
backup nor what was there before, and it looks like it worked.

Applied: restore step 3 is now "delete `bases/*.db-wal` and `*.db-shm`", with the reasoning written
down. The backup side is fine and needs no journal files: `BackupOne` uses SQLite's
`BackupDatabase`, which folds the WAL in.

Note, not a defect but a cost: `world.db` is 250 MB and `DefaultRetention` is 5. That is 1.2 GB in
`bases/backups` and a 250 MB copy on every start.

### #17 Refresh equipment bonuses after moving an item — MERGED

The hole is real and worth closing. The diagnosis, the value and the definition were all wrong.

**Fixed: the stated reason is false.**
The new comment says the cache builds "the characteristic sheet". It does not. The characteristic
sheet (`kub`) comes from `Managers.Equipment.Bonuses()` over the real inventory and was never stale
by this route. The cache feeds `StatsHandler.GetEquipBonus`, and through it the **combat** sheet —
max HP, initiative. Leaving that comment in is worse than leaving none: the next reader believes it.

**Fixed: three writers, one dictionary, two disagreements.**
Character selection, the inventory handler and now the equipment handler all fill
`SessionState.EquippedItems`, and they did not agree on either thing that matters:

| Writer                     | "worn" means   | value summed |
|----------------------------|----------------|--------------|
| CharacterSelectionHandler  | 0–62           | raw Value    |
| InventoryHandler           | 0–62           | raw Value    |
| EquipmentHandler (new)     | IsWorn, 0–15   | Sheet        |

Concrete: an item stored as `[[100,0,2,7]]` is worth 0 by one rule and 7 by the other. The same ring
gave different combat stats depending on whether it had been re-equipped since login, and reverted
on the next relog. And an item parked in slot 35 counted toward combat stats at login and stopped
counting the moment it moved.

Applied: one writer, `Equipment.RememberWorn(uid, position, effects)`, using `IsWorn` and `Sheet`.
`Sheet` is correct because it is what `Bonuses()` uses, so both sheets finally agree about the same
item. All three call sites converted.

**Fixed: cache removal was gated on `known`.**
`Managers.Equipment.LoadFrom` swallows its own exception, so a failed inventory read leaves `Items`
empty while the cache was already populated from character selection. From then on `known` is false
for every `iuk`, and the player can strip naked and keep fighting with the stats on for the rest of
the session.

Applied: removal is unconditional — if the slot is not worn, forget the uid. Only the *filling* half
needs to know the item.

### #25 Enforce monster spell cast limits

**BLOCKER — it emits a packet shape the captures say does not exist.**

### #29 Make active summons and Osamodas Gobgob functional

**Three unrelated things in one PR, one of which is data-destroying.** It also drags in the whole of
#26's healing pipeline, which is not in `main`. Please split into at least three.

**BLOCKER — the `V` and `v` masks are inverted, and it breaks 163 spell levels.**
The data settles it without ambiguity. Level 20821 (spell 3646) and above all level 45092
(spell 14968) carry a perfect staircase:

```
C,V100,v95  ->  C,V95,v90  ->  …  ->  C,V20,v0

V<N> is the CEILING, v<N> is the FLOOR.
The PR maps V -> vidaMinima and v -> vidaMaxima.
```

Consequences, all concrete:

- Spell 14968 grade 1: each of its twenty bands becomes `hp >= 100 && hp < 95` — impossible — so all
  twenty effect-792 hooks stop firing and the spell does literally nothing.
- The 33 sites with `v0` (the last rung of every staircase) become `hp < 0`, which nobody satisfies:
  the almost-dead band never triggers.
- Spell 4210: a target at 30% takes **two** damage bands at once (`A,v50` and `A,V20`), and one at
  70% takes the wrong band.

*Required:* swap them, and add a test built from the 45092 staircase — it is the cleanest oracle in
the dataset.

**DEFECT — two different rules resolve the grade of the same creature in one call.**
`Summons.Leer` looks for `grade == grado` and falls back to the *first* grade (`elegido ??= g`);
`GetMonsterGradeStats` does `Math.Clamp` and takes the *last*. Measured: 271 of the 4,770 effect
181/1011 entries have a spell grade higher than the template's grade count — e.g. spell 214 grade 6
against template 52, which has 5. Those summons get a grade-1 body (HP, AP, MP, resistances and now
elementals) with the grade-5 spell list. The correct grade travels in `efecto.DiceSide`
(`dice = 5144-2` -> template 5144, grade 2) and neither path reads it.

**DEFECT — it discards 67 of the 211 effect-1045 rows.**
The guard `if (efecto.DiceNum <= 0 || turnos <= 0) return null;` drops exactly the rows with
`value=0` and `diceSide=0`. That is not empty data — it means "set spell N's cooldown to 0", i.e.

## Part 3 — Patterns across the batch

These are not style preferences. Each appears in three or more of the fifteen, and each has already
cost real behaviour somewhere in this batch.

### A packet shape needs a capture, or it needs saying that it does not have one

Three PRs invent positioning or content for a frame. An independent scan of all 401 captures says
none of them invents an *opcode* — `jxc` appears 4,743 times, `jzu` 499, `jyy` 122 — so the instinct
is sound. What is not sound is asserting a shape the captures contradict (#25's populated monster
`jxc`) or a position they never show (#29's standalone `jxc`, #30's initiative-ordered placement
list).

If a capture supports it, name the file in the comment. If none does, say so in the PR body and let
it be reviewed as a guess.

### Comments in this repository are the protocol documentation

#23 deleted "37 of the 51 captured bars leave slot zero empty". #29 deleted the effect census. Those
sentences are the only record of measurements that took real work, and they are what stops the next
person changing the behaviour because it looked arbitrary. If a change makes a measured comment
wrong, **update the measurement** — do not delete it, and do not replace it with prose.

### Do not flip the README to ✅ while the gap is open

#23 and #25 both did. #23's spell bar repaints but `Fighter.Level` is never updated, so the engine
still resolves at the old level. #25 claims cast-in-line is enforced for players when `CastInLine`
appears nowhere in the server outside the schema. A 🟡 with the remaining gap written out is worth
more than a ✅ that has to be un-flipped.

### Rebase before you validate, and re-run the whole suite

Every PR in the batch cites 116, 343, 345, 346 or 347 tests. The suite was 462 when merging started
and is 492 now. Those numbers were measured against a `main` that is a hundred tests old — which is
also why #22 no longer compiled and #16's conflict would have deleted four package references.

### Check whether the code you are editing has a caller

A third of #23 and roughly half of #25 land on methods with no caller anywhere in the solution:
`SendSpellList`, `HandleTurnReadyAck`, `HandlePassTurnRequest`, `MonsterAI.ExecuteTurn`. The tree
even says so in a comment at `FightHandler.cs:1874-1879`. Two of #25's five tests exercise a path
that never runs, which means they pass and prove nothing.

### New code is English, identifiers and comments, since 26 Aug 2026

#20, #25, #26, #27, #28 and #29 all break it; #29 additionally ships two French log lines. Existing
Spanish code stays as it is — this is not a translation request, and mass-translating old code is
noise. It applies to what you add.

### One PR, one thing

#28 is a summon cap and a dialogue-close fix. #29 is a healing pipeline copied from #26, active
summons, and a mask change touching 163 spell levels. #26 and #29 both create the same new test
file. Splitting these is not bureaucracy: it is the only way the dangerous half can be rejected
without losing the good half.

### A guard that has never fired is a new feature, not a fix

#28's summon cap is the clearest case. `Otras[26]` was 0, so `if (tope > 0 && …)` never held and the
limit was dormant. Changing the base to 1 switches it on for the first time — and its failure path
spends the AP, logs a debug line and tells the client nothing. When you turn a dormant guard on, its
refusal path is new code and needs the same care as the guard itself.
